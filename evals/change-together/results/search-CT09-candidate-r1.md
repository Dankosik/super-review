## C-CT09-1: The retried-status set is stated twice, and this change updates only one copy

- Change anchor: `delivery/src/retry.rs`, `RETRY_STATUSES`. Old (D) was `&[502, 503]` and new (H) is `&[429, 502, 503]`. Partner, supporting context only: `webhooks/src/send.rs`, `should_redeliver`, whose body is `matches!(status, 502 | 503)`. The change moves one copy to include 429 and leaves the other holding the old value. That divergence was introduced by this change.
- Basis: rust.duplication.share-knowledge (repeated knowledge, old-value search). Not convention-only.
- Observation: the context states that both services retry outbound calls under one platform-documented policy for upstream status codes. The two functions encode that single decision with the same input and result types (`u16` to `bool`). Before the change they agreed on `{502, 503}`. Now `delivery` retries 429 and `webhooks` does not. Nothing connects the copies. A `contains` over a slice and a `matches!` are not exhaustive matches, and neither has a required field, so no compile error links them. A future edit to the policy has to be made in both places by hand, and this one was made in only one. The two services cannot be told apart by their purpose, since both retry outbound HTTP on upstream status, so the similarity is the same domain decision and not coincidence. I found no evidence that webhooks is meant to exclude 429. The only statement in the snapshot is the shared-policy context.
- Remedy: have one owner state the status set, with both services calling it. Only the owner is established. Which crate holds it is not, and no crate depends on another in the supplied snapshot. A minimal sketch: a shared location exports `pub fn retryable(status: u16) -> bool { matches!(status, 429 | 502 | 503) }`. `delivery` keeps calling it (or `RETRY_STATUSES` is re-exported from there), and `should_redeliver` delegates to it. The remaining tradeoff is a new shared-crate or dependency edge between the services, which is a decision for the project. The alternative is to keep two lists, which is justified only if webhooks has a deliberate, documented difference. The packet gives no such evidence. Either way, the 429 mismatch should be resolved explicitly: add 429 to `should_redeliver`, or record why webhooks excludes it.
- Preserve: the `delivery` public API is `RETRY_STATUSES` (a `pub const` slice) and `retryable`. Consumers of `RETRY_STATUSES` outside the snapshot are unverified, so keep the constant or re-export it. Webhook redelivery of 429 changes runtime behavior, which is a policy decision and not something the review can confirm. Retry count, backoff and ordering are not implicated.
- Affected files: inspected `delivery/src/retry.rs` and `webhooks/src/send.rs`. The call sites of `retryable` and `should_redeliver` were not supplied, and `Cargo.toml` shows only a single fixture package, so crate dependency direction is unknown.
