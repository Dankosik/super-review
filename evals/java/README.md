# Java judgment fixtures

These synthetic cases exercise competing change/retain decisions. They are not
live pull requests and do not establish snapshot provenance or native agent
orchestration. `cases.json` is a grader-only rubric. `packets/idioms.md` contains
neutral source/configuration evidence with opaque section IDs; do not send the
whole suite, case names, expected outcomes, or peer answers to a reviewer.

For a judgment evaluation, give a fresh specialist the shared contract, Java
context, the case's assigned lens and selected owner profiles, candidate format,
and only that packet section. Label it as a synthetic evaluation, not an acquired
GitHub snapshot. Supply the requested scope and effective policy neutrally. Grade
the returned observation and remedy separately against the rubric, actual code,
and strongest retain argument. Accept supported alternative remedies; do not
reward keyword mentions or require a finding in every case.

Record the model, reasoning setting, harness, instruction commit, exact packet,
raw result, supported findings, false positives, unsupported equivalence, missed
useful improvements, and policy/version handling. Repeat important cases and
reserve additional unseen production-like cases before making quality claims.
Do not copy expected answers or holdouts into runtime skill resources.

`bun test tests/java.test.ts` checks source acquisition, routing, rule identities,
profile ownership, resource isolation and fixture structure. `bun run validate`
checks installed links/identities and generated copies. These mechanical tests do
not prove that a model follows the instructions. No behavioral evaluation results
are claimed by adding this suite. Existing Go expectations and IDs are unchanged.
