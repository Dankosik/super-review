## Recommendations

### R-001 — Represent the decoder's active phase directly

**Location:** supplied `codec/src/lib.rs`, `Decoder` fields and `Decoder::{new,push,finish}`, especially `count: Option<u8>`, `pending: Option<(u8, u8)>`, `ended`, and `failed`; candidate F1. **Scope:** local, private representation.

The candidate's assertion that these fields are *all mutually exclusive at every point* is false. `finish` sets `failed` while a partial count or pending repetitions can remain; a nonempty `push` after the end marker sets `failed` while `ended` remains true. In the active, successful path, however, the code uses `count` and `pending` as alternative phases. A reader must combine the four fields with branch order to tell whether the next call needs a count, needs a value, drains repetitions, has ended, or returns `Failed`. A private data-carrying phase such as `NeedCount | NeedValue(u8) | Emit { remaining: u8, value: u8 } | Ended | Failed` would put that current obligation in one place and remove stale terminal combinations. Keep `max` and `reserved` outside the phase because the cumulative reservation persists across runs.

The present fields are compact and each branch is locally straightforward; the enum adds matching and transitions. The benefit is that callers of the private state no longer reconstruct or maintain cross-field phase invariants, especially at terminal transitions. Preserve the public signatures and error precedence: an errored call returns its first error, later calls return `Failed`; ended empty/nonempty pushes differ even with zero budget; pending output drains before input is consumed; a complete pair reserves its full count before output. Discarding latent active state on entry to `Failed` is compatible with the supplied terminal-error contract. This is a design recommendation, not a claim of tested equivalence.

### R-002 — Keep parsed CSV fields as text throughout parsing

**Location:** supplied `csv/src/main.rs`, `project`'s `str::from_utf8` conversion and `parse`'s byte scan with three `String::from_utf8(field)` conversions; candidate F2. **Scope:** local parser representation.

The original explanation conflates two operations. `parse` collapses doubled input quotes to one quote; `project` later doubles quotes while serializing output. The maintainability burden is narrower: after `project` validates the entire input as UTF-8, `parse` copies raw bytes into a `Vec<u8>` and treats each completed field conversion as independently fallible. The reader must establish that the byte scanner never splits a multibyte character at a field boundary. Collecting decoded field text directly in `String` while traversing `char` values makes that property follow from the input and field types and removes the repeated conversion/error branches. Retain the existing `State` transitions and explicit treatment of ASCII CSV syntax; this is a local representation change, not a parser redesign or dependency request.

The current byte scan has a real advantage: the dialect delimiters are ASCII, and copying non-delimiter bytes is direct. A character iterator adds UTF-8 decoding and must still distinguish doubled quotes, embedded CR/LF, CRLF terminators, blank lines, and EOF. The net reading benefit is nevertheless concrete because the field representation matches the parsed value used by `project`, and UTF-8 validation has one visible owner. Keep whole-document parsing before header and width checks, preserve error precedence and withheld stdout on invalid input, and continue escaping quotes only during output serialization. No behavior or performance equivalence was executed.

The recommendations affect separate crates and can be considered independently.
