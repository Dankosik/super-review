## C-q07-1: Decoder phase is split across two options and two terminal flags

- Change anchor: Whole supplied `src/lib.rs`, `Decoder` fields `count: Option<u8>`, `pending: Option<(u8, u8)>`, `ended: bool`, and `failed: bool`; `Decoder::push` checks `failed` then `ended`, drains `pending`, takes `count`, and finally reads a new count. `Decoder::finish` separately checks the terminal flags. No H/D comparison applies.
- Basis: `rust.representation.express-concepts`; no convention-only advice.
- Observation: These fields describe one phase of a decoder, yet their legal combinations and priority are reconstructed from the method's branch order. A reader must establish that pending repetitions and a count awaiting its value never coexist, and that a terminal flag cannot coexist with unfinished work. The code maintains those relationships, but every change to a transition or terminal check requires rechecking them across both methods.
- Remedy: A private phase enum can give the existing states one home, for example `AwaitCount`, `AwaitValue(u8)`, `Emit { remaining: u8, value: u8 }`, `Ended`, and `Failed`, held in one `phase` field. Reading a count enters `AwaitValue`; accepting its value enters `Emit`; draining it returns to `AwaitCount`; end marker and first error enter their respective terminal states. This removes the cross-field exclusivity and flag-priority relationships while leaving output-budget control and the cumulative cap with `push`. The strongest keep alternative is the current compact branch sequence, whose actual transitions already maintain valid states; the enum adds matching code, but makes the phase protocol explicit at construction and in both public methods. This is a representation illustration, not a tested rewrite.
- Preserve: Keep the public `Decoder`, `Decoded`, and `Error` shapes and all call behavior: `Failed` precedes other conditions; after `Ended`, empty pushes succeed even with zero budget and nonempty pushes fail; active zero-budget pushes do no work; pending output drains before input; a count can await a later value; `finish` does not drain output. Error calls discard that call's output. The internal enum must not change the order in which wire bytes are inspected or cap errors occur. No downstream use of private fields is supplied; public-consumer compatibility beyond the stated API was not independently checked.

## C-q07-2: Decoder stores both the cap and its consumed reservation

- Change anchor: Whole supplied `src/lib.rs`, `Decoder` fields `max: usize` and `reserved: usize`, initialized in `Decoder::new`; the complete-pair path in `Decoder::push` uses `if count > self.max - self.reserved` and then `self.reserved += count`. No H/D comparison applies.
- Basis: `rust.representation.express-concepts`; no convention-only advice.
- Observation: No supplied method needs the original cap or total reservation independently; it needs only the space remaining for the next accepted pair. The two fields make the reader maintain `reserved <= max` to understand the subtraction and inclusive cap, and the same relationship must be preserved by any later pair-acceptance edit.
- Remedy: Store `remaining_capacity: usize`, initialized from `max_decoded_bytes`. At complete-pair acceptance, compare `count` with `remaining_capacity` and subtract it only after acceptance. That keeps one current fact, removes the `max`/`reserved` relationship, and leaves the existing pair-acceptance point as its owner. The strongest keep alternative is that `max` and `reserved` name the cumulative accounting explicitly; here neither value has another observed use, so the extra relationship carries no demonstrated benefit. This local replacement does not depend on the phase-enum proposal.
- Preserve: Reserve all repetitions of a complete pair before emitting any of that pair, including output deferred to later calls. A count awaiting a value does not consume capacity. Keep the cap inclusive and correct at `usize::MAX`, with the same first-error and terminal behavior. The constructor parameter and public API stay unchanged. No external consumer source was supplied; the proposed field is private.
