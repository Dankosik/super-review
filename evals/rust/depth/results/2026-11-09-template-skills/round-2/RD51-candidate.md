## C-RD51-1: Two `u64` aliases leave identifier roles to argument position

- Change anchor: `src/lib.rs`, whole-project snapshot. `pub type CustomerId = u64; pub type OrderId = u64;`, `Refund::new(customer: CustomerId, order: OrderId, cents: u64)`, and `refund_for(order: OrderId, customer: CustomerId, cents: u64) -> Refund`. The pair `Refund::new(customer, order, ...)` and `refund_for(order, customer, ...)` is the supporting evidence. The aliases are the only representation of the two concepts.
- Basis: `rust.representation.express-concepts`. The rule says a type alias names a type but gives the concept no home, and that a newtype gives identifiers sharing a primitive their own concept. Not convention-only.
- Observation: `CustomerId`, `OrderId` and `cents` are all `u64`, so the aliases are interchangeable with each other and with the amount. Which value is which is carried only by argument position. This is already visible in the code: `refund_for` takes `(order, customer, cents)` while `Refund::new` takes `(customer, order, cents)`, and `refund_for` re-orders the arguments by hand. A reader must remember that the two functions disagree and that the swap is deliberate. A fully consistent call that silently transposes the identifiers would read the same. The context says the two identifiers come from the same database and have the same width, so the primitive gives no distinguishing information. The cost described here is reading and maintenance cost, assuming the code works as intended.
- Remedy: give each identifier its own newtype and, if the amount is also meant to be a distinct concept, a small `Cents` newtype. Sketch: `pub struct CustomerId(u64); pub struct OrderId(u64);` with the existing signatures unchanged apart from the types, and with `Refund` fields typed the same way. The transposition between `refund_for` and `Refund::new` is then visible in the types instead of being remembered. Strongest keep alternative: leave the aliases and unify the parameter order of `refund_for` with `Refund::new`. That removes the visible disagreement but leaves the identifiers interchangeable. Which of the two to adopt is a tradeoff the maintainer can weigh. The amount newtype is optional and only worthwhile if the amount has other operations or a distinct meaning.
- Preserve: the module is private and unreleased with no external API commitment, so changing the public signatures is within scope. Accessors, field values and the `u64` payload keep their meaning. Database encoding is not shown. If the identifiers are bound to a database layer or serialized, add the matching conversions (`From<u64>` or derive support) so the wire and storage forms stay the same. Consumers outside the supplied files were not inspected.
- Affected files: `src/lib.rs` (inspected). Callers of `Refund::new` and `refund_for` outside the packet: still needed.

## C-RD51-2: Getters restate the field list of passive data, with no invariant behind them

- Change anchor: `src/lib.rs`, whole-project snapshot. `struct Refund { customer, order, cents }` with private fields, `Refund::new`, and the getters `customer()`, `order()`, `cents()`.
- Basis: `rust.representation.express-concepts`. Getters over private fields of passive internal data restate the field list, and an invariant-bearing field belongs behind its operations. Not convention-only.
- Observation: the fields are private only to be re-exposed unchanged. Each getter returns a `Copy` value with no derived computation. The context states `Refund::new` performs no validation, so no field has an invariant that privacy protects, and the type is module-internal data. The reader must read the field declarations, the constructor and three one-line accessors to learn that this is a plain triple. Adding a field means editing the struct, `new` and a getter. The cost is the repeated field list. It is not a bug.
- Remedy: make the fields `pub` and drop the three getters (keep `new` only if its positional constructor is wanted). Strongest keep alternative: keep the private fields if the author expects to add validation or change the layout later. The scope states the type is private and unreleased, and no such requirement appears in the source, so that tradeoff stays with the maintainer. If C-RD51-1 is adopted, `new` still takes the typed values. Public fields also let callers use struct-literal syntax with field names, which would remove the positional-order burden for the identifiers even without newtypes. The two remedies compose.
- Preserve: the `u64` or newtype values are `Copy`, so direct field reads match the getters' by-value returns. No trait implementations, derives or serialization are present to be disturbed. A caller that relied on the type being non-constructible by struct literal would lose that. The context says there is no validation, so no such contract is established. Consumers were not inspected.
